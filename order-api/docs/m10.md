# M10: Consistency and caching

This module is about two things: keeping orders correct when many requests hit the same data at once, and making reads faster with a cache without serving out-of-date orders.

## 1. Twenty people paying the same order

**Test:** `OrderConcurrencyTests.concurrentPayOnlyOneWins` sends PAY for one order from 20 threads at the same moment.

**Result:** one `200`, nineteen `409`.

**Why:** every order has a version number. All 20 requests read the order at version 0. The first one to save moves it to version 1. The other 19 try to save saying "I expect version 0", Spring Data's `@Version` check sees the mismatch, and the API answers `409 Conflict`. The order is paid exactly once and no update is silently lost.

## 2. The same order created ten times

**Test:** `OrderConcurrencyTests.concurrentDuplicateCreateMakesOneOrder` sends the same create request 10 times in parallel with the same `Idempotency-Key`.

**Result:** ten `201`s, but only one order in the database.

**Why:** the key is saved as the `_id` of a document in `idempotency_keys`, and MongoDB never allows two documents with the same `_id`. So only one insert wins. The other nine get a duplicate-key error and are handed back the order the winner created. A client can retry as often as it likes without creating duplicates.

## 3. Caching GET /orders/{id}

- `OrderService.get` has `@Cacheable("orders")`. The first read of an order goes to MongoDB, and later reads come from memory.
- `OrderService.apply` has `@CacheEvict` for that order's id. After PAY, SHIP or CANCEL, the cached copy is thrown away, so the next read goes back to MongoDB and sees the new status.
- Caching is switched on by `@EnableCaching` in `config/CacheConfig`. `spring-boot-starter-cache` provides a simple in-memory cache by default.

This pattern is called **cache-aside**: check the cache, and on a miss load from the database and keep the result.

One detail: the caching is done by a proxy that Spring wraps around `OrderService` (the startup log shows `OrderService$$SpringCGLIB$$0`). A call from one method to another inside the same class doesn't go through the proxy, so when `apply()` calls `get()` it skips the cache. That's what I want, because before changing an order I want the real copy from the database.

## 4. Proving the cache is cleared after a change

**Test:** `OrderCacheTests.actionEvictsCachedOrder` reads an order (cached as NEW), pays it, then reads it again and expects PAID.

With `@CacheEvict` removed, the test fails:

    OrderCacheTests.actionEvictsCachedOrder:33 expected: <PAID> but was: <NEW>

The order was paid in MongoDB, but the old copy was still being served from the cache. With `@CacheEvict` back, the test passes.

## 5. A problem I hit: @EnableCaching broke the web tests

I first put `@EnableCaching` on `OrderApiApplication`. The cache tests passed, but the full test run had 9 errors. Every test in `OrderControllerWebTests` and `OrderResponseContractTests` failed to start with:

    A component required a bean of type 'org.springframework.cache.CacheManager' that could not be found.

**Cause:** those tests use `@WebMvcTest`, which starts only the web layer and doesn't create a `CacheManager`. They still read the annotations on the main application class, though, so caching was switched on with nowhere to store anything.

**Fix:** I moved `@EnableCaching` into its own class, `config/CacheConfig`. The full app still picks it up, but `@WebMvcTest` skips `@Configuration` classes, so the web tests start again. All 38 tests pass.

**Lesson:** keep feature switches like `@EnableCaching` off the main application class so test slices don't inherit them.

## 6. The cache's weak spot: writes that skip the service

**Test:** `OrderCacheTests.writeThatBypassesTheServiceGivesStaleRead` changes an order's status directly in MongoDB instead of through the service. Nothing clears the cache, so the API keeps returning NEW while the database says CANCELLED.

So the cache is only correct as long as every write goes through `OrderService`. A script, another service or a manual fix in mongosh would leave it stale until the app restarts.

## 7. Not built, but how I'd handle them

- **Transactions:** in M6 I tried `@Transactional` with `MongoTransactionManager`, and the standalone mongod refused: "Transaction numbers are only allowed on a replica set member or mongos". Multi-document transactions need a replica set. Here each write touches only one document, and single-document writes in MongoDB are already atomic, so I didn't need one.
- **Expiry (TTL):** this simple cache never expires entries. In production I'd use something like Caffeine with an expiry, so that even a missed eviction is only stale for a limited time.
- **Stampede:** if a popular order isn't cached and many requests arrive at once, they all hit MongoDB together. `@Cacheable(sync = true)` lets one request load it while the others wait for its result.
