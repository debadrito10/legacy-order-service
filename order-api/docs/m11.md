# M11: Docker and secure images

## The image

`order-api/Dockerfile` has two stages:

- **Build stage** (`eclipse-temurin:25-jdk`): copies the Maven wrapper and `pom.xml` first and runs `dependency:go-offline`, then copies `src` and runs `package -DskipTests`. Tests are skipped here because they need MongoDB, which doesn't exist inside the build, and they already pass outside it.
- **Runtime stage** (`eclipse-temurin:25-jre`): copies only the JAR from the build stage. The JDK, Maven and the downloaded dependencies never reach the final image.

Both base images come from `mirror.gcr.io`, because Docker Hub downloads fail on my network.

`.dockerignore` keeps `target`, `.idea`, `*.iml` and `docs` out of the build context.

## Layers and size

The first build took about 52 s (`go-offline` 25.8 s, `package` 7.9 s).

Because `pom.xml` is copied before `src`, the dependencies get their own layer. If I change only Java code, Docker reuses that layer from cache and only the `package` step runs again.

`docker images order-api` shows **156 MB** content size (compressed) and **567 MB** on disk. Most of that is the JRE.

## Reproducible build

- The Maven wrapper pins Maven 3.10.0, and the pom pins every dependency version.
- The base images are tags (`25-jdk`, `25-jre`), and tags can move to newer images later. The build log shows the exact digests it used, e.g. `eclipse-temurin:25-jre@sha256:4ed132f6832e...`. Pinning `FROM` to the digest would make the base image fully fixed too.

## Non-root and memory

**Non-root:** `useradd` creates a system user `app` with uid 1001, and `USER app` means the JVM doesn't run as root. The startup log confirms it:

    /app/app.jar started by app in /app

**Memory:** `JAVA_TOOL_OPTIONS=-XX:MaxRAMPercentage=75` makes the JVM size its heap from the container's memory limit instead of the whole machine's. The log shows:

    Picked up JAVA_TOOL_OPTIONS: -XX:MaxRAMPercentage=75

## Startup error I reproduced

Running the image with no configuration:

    docker run --rm -p 18080:18080 order-api:m11

It didn't start:

    Exception in monitor thread while connecting to server 127.0.0.1:27018
    Caused by: java.net.ConnectException: Connection refused
    Waiting for server to become available for operation createIndexes ... Remaining time: 29992 ms
    Timed out while waiting for a server that matches WritableServerSelector
    Application run failed

**Why it couldn't connect:** `application.yaml` points at `mongodb://127.0.0.1:27018`. Inside a container, `127.0.0.1` is the container itself, not my laptop, so nothing was listening.

**Why it failed at startup instead of just showing health DOWN:** because of `auto-index-creation` from M9. Spring creates the compound index while starting, so startup needs MongoDB. The driver waited its 30 s server-selection timeout, then the app exited. `curl` to `/actuator/health` got "Empty reply from server" because the app was shutting down.

Auto index creation is convenient, but it ties startup to the database. In production I'd create indexes as a separate step.

## Fix

I started MongoDB in its own container and pointed the app at it through the host:

    docker run -d --name m11-mongo -p 27019:27017 mirror.gcr.io/library/mongo:8.0
    docker run --rm -p 18080:18080 -e SPRING_MONGODB_URI=mongodb://host.docker.internal:27019/orders order-api:m11

- `host.docker.internal` is how a container reaches the host machine on Docker Desktop.
- The environment variable overrides `spring.mongodb.uri` without rebuilding the image.

The app started in 4.8 s and health was UP.

My first attempt on 27019 failed with "port is already allocated", because two old containers (`m9-mongo`, `m10-mongo`) were still running from an earlier attempt. `docker ps -a` showed them, and I removed them.
