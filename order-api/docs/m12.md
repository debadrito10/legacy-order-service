# M12: Compose and local dependencies

## The stack

`order-api/compose.yaml` runs two services on one Compose network:

- **mongo:** `mirror.gcr.io/library/mongo:8.0`, data in the named volume `mongo-data`, and a healthcheck that runs `db.adminCommand('ping')` with mongosh every 5 s.
- **api:** built from the M11 Dockerfile, port 18080 published, configuration from `.env`, and `depends_on` mongo with `condition: service_healthy`.

mongo has no `ports` section, so only the api can reach it. That also means it can't clash with anything already using a port on my laptop.

## Why the URI says mongo, not localhost

`.env` sets:

    SPRING_MONGODB_URI=mongodb://mongo:27017/orders

Compose gives every service a DNS name on the network, so `mongo` resolves to the Mongo container. The api log shows it: `hosts=[mongo:27017]`, then:

    Monitor thread successfully connected to server ... address=mongo:27017

Inside a container, `localhost` or `127.0.0.1` means that container itself. That's exactly why the default URI `127.0.0.1:27018` gave "Connection refused" in M11.

## Readiness on startup

`docker compose up -d --build` showed:

    Container order-api-mongo-1  Healthy   6.5s
    Container order-api-api-1    Started   6.6s

docker compose ps:

    NAME                IMAGE                             SERVICE   STATUS                    PORTS
    order-api-api-1     order-api:m12                     api       Up 20 seconds             0.0.0.0:18080->18080/tcp
    order-api-mongo-1   mirror.gcr.io/library/mongo:8.0   mongo     Up 26 seconds (healthy)   27017/tcp

mongo shows 27017/tcp with no host mapping: reachable on the Compose network only.

The api waited until mongo's healthcheck passed. "Container started" isn't enough for a database, because mongod takes a moment before it accepts connections. Without the health condition, the api could start first and, because of `auto-index-creation`, fail the same way it did in M11.

Here it started in 4.36 s with health UP.

## DNS failure I reproduced

I changed `.env` to `mongodb://mongodb:27017/orders` (wrong service name) and ran `docker compose up -d`. The api log:

    com.mongodb.MongoSocketException: mongodb: Name or service not known
    Caused by: java.net.UnknownHostException: mongodb: Name or service not known

There's no service called `mongodb` on the network, so the name doesn't resolve at all. That's a different failure from M11:

- **M11:** the address existed, but nothing was listening on it (Connection refused).
- **Here:** the name itself doesn't exist (UnknownHostException).

After the driver's 30 s timeout, the app exits. I changed `.env` back to `mongo`, ran `docker compose up -d`, and health was UP again.

## Readiness failure and recovery

With everything running, I stopped only the database:

    > docker compose stop mongo
     Container order-api-mongo-1  Stopped

    > curl.exe -i http://localhost:18080/actuator/health
    HTTP/1.1 503
    X-Correlation-Id: c9f1f4db-754f-4ef3-9cde-bdd8bfd6889d
    Content-Type: application/vnd.spring-boot.actuator.v3+json
    Connection: close

    {"groups":["liveness","readiness"],"status":"DOWN"}

The api process kept running, but its health check reports that its dependency is gone. The 503 tells a load balancer or orchestrator not to send it traffic.

    > docker compose start mongo
     Container order-api-mongo-1  Started

    > curl.exe -i http://localhost:18080/actuator/health
    HTTP/1.1 200
    X-Correlation-Id: 1e4b4357-8246-4ec9-b911-dc8e182f7c9b
    Content-Type: application/vnd.spring-boot.actuator.v3+json

    {"groups":["liveness","readiness"],"status":"UP"}

The X-Correlation-Id header comes from the M7 correlation filter, still working inside the container.

The MongoDB driver reconnected by itself. No api restart was needed.

## Secrets hygiene

- `.env` holds the real values. It's in `.gitignore` and `.dockerignore`, so it's never committed and never copied into an image.
- `.env.example` is committed and shows which variables need setting.
