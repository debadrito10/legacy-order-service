## The manifests

order-api/k8s/, numbered so kubectl apply -f k8s/ creates them in the right order (files are applied alphabetically, and the namespace must exist first):

- 00-namespace.yaml: namespace noduco-orders, so this app is separate from anything else in the cluster.
- 10-config.yaml: ConfigMap order-api-config (NODUCO_ORDERS_CURRENCY=INR, readiness group includes mongo) and Secret order-api-secret (SPRING_MONGODB_URI). The api reads both with envFrom.
- 20-mongo.yaml: mongo Deployment (1 replica) and mongo Service.
- 30-api.yaml: api Deployment (2 replicas) and api Service.

## Choices

Image: order-api:m13, the M11 image retagged. imagePullPolicy IfNotPresent, so the node uses the locally built image instead of looking for it in a registry.

Config vs secret: plain settings go in the ConfigMap, the connection string goes in the Secret. This URI has no password so committing it is harmless here; a real one would not be committed.

Labels and selectors: each Service selects pods with app: api or app: mongo. A pod gets traffic only if its labels match and it is Ready.

Probes:
- api readiness: GET /actuator/health/readiness every 5 s. The readiness group includes readinessState and mongo, so a pod is Ready only when Spring has started and MongoDB is reachable.
- api liveness: GET /actuator/health/liveness, first check after 30 s. It does not include mongo: if MongoDB is down the pods are taken out of the Service but not restarted, because a restart would not fix the database.
- mongo readiness: TCP check on 27017.

Resources: api requests 250m CPU and 384Mi, memory limit 512Mi. With MaxRAMPercentage=75 from the image, the heap is about 384Mi of the 512Mi limit. mongo requests 100m and 256Mi, limit 512Mi.

Rollout: RollingUpdate with maxUnavailable 0 and maxSurge 1. A new pod has to become Ready before an old one is removed, so a bad release cannot reduce capacity.

Storage: mongo uses emptyDir, so data is lost if the pod is deleted. Fine for a lab; production would use a StatefulSet with a PersistentVolumeClaim.

## Predictions before applying

1. How many pods? Three: one for Mongo and two for the API, because replicas is 2. The ConfigMap, Secret and Services don't make pods.
2. Ready straight away? No. Spring Boot takes a few seconds to start, and the readiness probe won't pass until the health endpoint says UP.
3. How many endpoint addresses? Two, one per API pod.
4. How does the API find mongo? Through the mongo Service.

Three pods, as predicted. The api pods were Running but 0/1 from 3 s to 14 s: the process was up but readiness had not passed yet. Running is not the same as Ready, and only Ready pods get traffic.

    service/mongo   ClusterIP   10.99.187.124   <none>        27017/TCP   46s
    endpoints/api     10.1.0.6:18080,10.1.0.8:18080   46s
    endpoints/mongo   10.1.0.7:27017                  46s

The Deployment creates a ReplicaSet (the ccc7b5c99 in the pod names is its hash), and the ReplicaSet creates the pods. The api Service has two endpoints, one per Ready pod, as predicted. kubectl warns that v1 Endpoints is deprecated in favour of EndpointSlices, which hold the same information.

How the api finds mongo, in more detail: the cluster DNS (CoreDNS) resolves mongo inside the noduco-orders namespace to the Service's ClusterIP 10.99.187.124 (full name mongo.noduco-orders.svc.cluster.local). kube-proxy forwards that to the Ready pod behind it, 10.1.0.7:27017. Pod IPs change when pods are recreated; the Service name and ClusterIP do not, which is why the URI uses the Service name.
