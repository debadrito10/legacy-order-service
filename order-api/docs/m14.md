# M14: kubectl and service health

Starting point: the M13 deployment in namespace noduco-orders, two api pods (ReplicaSet ccc7b5c99) and one mongo pod, all Ready. I broke the live Deployment twice on purpose, diagnosed each failure with read-only kubectl commands and recovered with rollout undo. The manifests in k8s/ were never changed.

## Break 1: bad image tag

Prediction: the two old pods keep running. Kubernetes starts one new pod, but it can't pull the image, so it gets stuck and never becomes Ready. Because of maxUnavailable: 0 the old pods aren't removed, so the rollout just hangs and the API stays up.

    > kubectl set image deployment/api api=order-api:m13-typo -n noduco-orders
    deployment.apps/api image updated

    > kubectl get pods -n noduco-orders
    NAME                   READY   STATUS         RESTARTS   AGE
    api-7fb6749584-5hff6   0/1     ErrImagePull   0          40s
    api-ccc7b5c99-8cfvx    1/1     Running        0          16m
    api-ccc7b5c99-k5l2q    1/1     Running        0          16m
    mongo-8d9976dc-hlsmf   1/1     Running        0          16m

The new pod has a different hash (7fb6749584) because changing the image changed the pod template, so the Deployment created a new ReplicaSet.

    > kubectl rollout status deployment/api -n noduco-orders --timeout=20s
    Waiting for deployment "api" rollout to finish: 1 out of 2 new replicas have been updated...
    error: timed out waiting for the condition

    > kubectl describe pod -n noduco-orders api-7fb6749584-5hff6   (Events)
    Normal   Pulling    50s (x3 over 90s)  kubelet  Pulling image "order-api:m13-typo"
    Warning  Failed     48s (x3 over 87s)  kubelet  Failed to pull image "order-api:m13-typo": ... failed to resolve reference "docker.io/library/order-api:m13-typo": docker.io/library/order-api:m13-typo: not found
    Warning  Failed     48s (x3 over 87s)  kubelet  Error: ErrImagePull
    Normal   BackOff    8s (x5 over 86s)   kubelet  Back-off pulling image "order-api:m13-typo"
    Warning  Failed     8s (x5 over 86s)   kubelet  Error: ImagePullBackOff

    > curl.exe http://localhost:18080/actuator/health
    {"groups":["liveness","readiness"],"status":"UP"}

Diagnosis: with imagePullPolicy IfNotPresent the node uses a local image if it has one. order-api:m13-typo is not local, so it tried docker.io, where it doesn't exist either. ErrImagePull is the failed attempt; ImagePullBackOff means Kubernetes keeps retrying with longer waits. The container never started, so there are no app logs to read. Users were not affected: the old pods kept serving and health stayed UP.

The rollout does not fail or roll back by itself. After progressDeadlineSeconds (600 s by default) the Deployment is marked ProgressDeadlineExceeded, but the bad pod stays until someone acts. In a pipeline, a step waiting on kubectl rollout status would catch it.

Recovery:

    > kubectl rollout undo deployment/api -n noduco-orders
    deployment.apps/api rolled back
    > kubectl rollout status deployment/api -n noduco-orders
    deployment "api" successfully rolled out
    > kubectl get pods -n noduco-orders
    api-7fb6749584-5hff6   0/1     Terminating   0          2m22s
    api-ccc7b5c99-8cfvx    1/1     Running       0          18m
    api-ccc7b5c99-k5l2q    1/1     Running       0          18m
    > kubectl rollout history deployment/api -n noduco-orders
    REVISION  CHANGE-CAUSE
    2         <none>
    3         <none>

The original pods were never restarted (still 18m, 0 restarts). There is no revision 1 in the history: undo re-applied revision 1's template as a new revision 3. CHANGE-CAUSE is empty because nothing recorded why each change was made; annotating the Deployment with kubernetes.io/change-cause would fill it in.

## Break 2: wrong readiness probe path

Prediction: the new pod won't be restarted, because only readiness is broken and liveness still passes. It won't get any traffic either, since a 404 means it never becomes Ready. So the rollout gets stuck again like last time, and the two old pods keep running and serving requests.

I changed the readiness path from /actuator/health/readiness to /actuator/health/ready with kubectl edit deployment api.

    > kubectl get pods -n noduco-orders
    NAME                   READY   STATUS    RESTARTS   AGE
    api-5b79997756-h6f9f   0/1     Running   0          37s
    api-ccc7b5c99-8cfvx    1/1     Running   0          21m
    api-ccc7b5c99-k5l2q    1/1     Running   0          21m

Still 0/1 at 37 s with 0 restarts. A healthy pod is Ready at about 14 s, and liveness starts checking at 30 s, so liveness is passing and only readiness is failing.

    > kubectl describe pod -n noduco-orders api-5b79997756-h6f9f
    State:          Running
    Ready:          False
    Restart Count:  0
    Readiness:      http-get http://:18080/actuator/health/ready delay=0s timeout=1s period=5s #success=1 #failure=3
    Events:
    Normal   Started    54s                kubelet  Started container api
    Warning  Unhealthy  50s (x3 over 53s)  kubelet  Readiness probe failed: Get "http://10.1.0.10:18080/actuator/health/ready": dial tcp 10.1.0.10:18080: connect: connection refused
    Warning  Unhealthy  0s (x10 over 45s)  kubelet  Readiness probe failed: HTTP probe failed with statuscode: 404

The probe message changed over time. Connection refused means the app had not opened its port yet, which is normal during startup. 404 means the app was answering but the path did not exist. The wrong path is visible in the pod spec itself.

    > kubectl logs -n noduco-orders api-5b79997756-h6f9f --tail 5
    ... LifecycleProbe : LIFECYCLE 3 ApplicationReadyEvent: every bean built, Tomcat accepting requests
    ... Initializing Spring DispatcherServlet 'dispatcherServlet'

    > kubectl get endpoints api -n noduco-orders
    api    10.1.0.6:18080,10.1.0.8:18080

The app started fine. The new pod's IP 10.1.0.10 is not in the endpoints, so the Service sends it no traffic.

To prove only the probe was wrong, I port-forwarded to the new pod directly:

    > kubectl port-forward -n noduco-orders pod/api-5b79997756-h6f9f 18081:18080
    > curl.exe http://localhost:18081/actuator/health/readiness
    {"status":"UP"}
    > curl.exe -i http://localhost:18081/actuator/health/ready
    HTTP/1.1 404

Same pod: the real readiness path says UP, the configured one is 404.

Kubernetes treats HTTP 200-399 as probe success and anything else as failure. A failing readiness probe only removes the pod from the Service; it never restarts the container. If the same wrong path had been on the liveness probe, the container would be restarted every few failures and end up in CrashLoopBackOff.

Recovery:

    > kubectl rollout undo deployment/api -n noduco-orders
    > kubectl rollout status deployment/api -n noduco-orders
    deployment "api" successfully rolled out
    > kubectl get pods -n noduco-orders
    NAME                   READY   STATUS    RESTARTS   AGE
    api-ccc7b5c99-8cfvx    1/1     Running   0          24m
    api-ccc7b5c99-k5l2q    1/1     Running   0          24m
    mongo-8d9976dc-hlsmf   1/1     Running   0          24m

The same two original pods, 24 minutes old with 0 restarts, served traffic through both breaks.

## How I would isolate a failure next time

1. kubectl get pods: is the container running at all? Pending with ImagePullBackOff means it can't start (image, registry, tag). Running but 0/1 means it started but is not Ready (probe or dependency). Restarts climbing or CrashLoopBackOff means the process keeps dying or liveness keeps failing.
2. kubectl describe pod: the Events section names the reason (pull error, probe status code, OOMKilled) and the spec shows the configured image and probe paths.
3. kubectl logs: only useful once the container has started. For a restarting container, kubectl logs --previous shows the last run.
4. kubectl get endpoints (or endpointslices): which pods are actually receiving traffic.
5. kubectl port-forward to a single pod: test that pod directly without touching the Service.

All of these are read-only. In both breaks I did not delete pods, restart anything or edit running containers. maxUnavailable: 0 kept the working pods serving the whole time, and rollout undo returned the Deployment to a known-good template.
