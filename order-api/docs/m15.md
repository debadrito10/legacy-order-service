# M15: Resilience and configuration security

All experiments ran on the M12 Compose stack (api + mongo), rebuilt with the changes below.

## What I changed

Timeouts on the MongoDB connection string (application.yaml, .env, .env.example, k8s/11-secret.yaml and its example):

    ?serverSelectionTimeoutMS=2000&connectTimeoutMS=2000&socketTimeoutMS=3000

- serverSelectionTimeoutMS=2000: if no MongoDB server is reachable, give up after 2 s. The default is 30 s, which is the wait I saw in M11.
- connectTimeoutMS=2000: limit on opening a connection.
- socketTimeoutMS=3000: limit on waiting for a reply once connected. This is what catches a slow database.

The test that uses application.yaml's own URI logs serverSelectionTimeout='2000 ms', connectTimeoutMS=2000, readTimeoutMS=3000, so the options are applied.

ApiExceptionHandler now maps DataAccessResourceFailureException (what Spring turns MongoDB timeouts and connection failures into) to 503 Service Unavailable with Retry-After: 2 and a database-unavailable Problem Details body. A 503 with Retry-After says the failure is temporary and when to try again; the generic handler would have returned 500, which says nothing about retrying.

OrderService takes over abandoned Idempotency-Key claims (see experiment 3).

## Experiment 1: MongoDB down

    > docker compose stop mongo
    > curl.exe -s -i -w "time: %{time_total}s" -X POST http://localhost:18080/orders ... --data-binary "@docs/m15-order.json"
    HTTP/1.1 503
    X-Correlation-Id: d6f771bf-b74c-46a2-8096-67d85249be8d
    Retry-After: 2
    Content-Type: application/problem+json

    {"detail":"The order database did not answer in time. Retry later with the same Idempotency-Key.","instance":"/orders","status":503,"title":"Database unavailable","type":"https://noduco.example/problems/database-unavailable","correlationId":"d6f771bf-b74c-46a2-8096-67d85249be8d"}
    time: 2.200811s

The api log has the same correlation id, so a failed request can be traced to its log line:

    WARN [d6f771bf-b74c-46a2-8096-67d85249be8d] ... ApiExceptionHandler : Database unavailable: Timed out while waiting for a server ... caused by {java.net.UnknownHostException: mongo}

The cause is UnknownHostException, not connection refused: when a Compose container is stopped, its name is removed from the network's DNS.

    > docker compose start mongo
    > curl.exe ... (same request)
    HTTP/1.1 201
    Location: /orders/6b059a5d67345edb6f9a3542
    time: 0.075852s

2.2 s to a clear 503 instead of 30 s, and recovery without restarting the api: the driver reconnects by itself.

## Experiment 2: MongoDB slow, client retries without an Idempotency-Key

db.fsyncLock() keeps MongoDB running but makes every write wait.

    > docker compose exec mongo mongosh --quiet --eval "db.fsyncLock()"
    { info: 'now locked against writes, use db.fsyncUnlock() to unlock', lockCount: Long('1'), ok: 1 }

Same order sent twice, like a client retrying after a timeout:

    HTTP/1.1 503   Retry-After: 2   time: 3.036556s
    HTTP/1.1 503   Retry-After: 2   time: 3.020131s

About 3 s each: the server was reachable, so the 3 s socket timeout fired instead of the 2 s server selection timeout.

    > docker compose exec mongo mongosh --quiet --eval "db.fsyncUnlock()"
    > db.orders.countDocuments({customer:'m15'})
    3

There was 1 order before. Both "failed" writes were queued in MongoDB and completed after the unlock, so one customer intent became two orders.

A timeout does not mean the write failed; it means the client does not know. Retrying a write with nothing that identifies it as the same request is an uncontrolled retry, and it creates duplicates.

## Experiment 3: MongoDB slow, client retries with an Idempotency-Key

Same scenario, both requests with Idempotency-Key: m15-key-1. Both returned 503 after about 3 s (3.094497 s, 3.017889 s).

After the unlock:

    > db.orders.countDocuments({customer:'m15'})
    3
    > db.idempotency_keys.findOne({_id:'m15-key-1'})
    { _id: 'm15-key-1', fingerprint: 'm15|1500', createdAt: ISODate('2026-11-24T14:13:14.358Z') }

No duplicate: the key worked. But no order either, and the claim has no orderId. The claim insert was the write that got frozen; the request gave up, then the claim landed with nothing left to finish it. A retry five minutes later:

    HTTP/1.1 409
    {"detail":"A request with Idempotency-Key m15-key-1 is still being processed; retry later", "title":"Request still in progress", ...}

It would have said that forever. The key prevented the duplicate but the customer could never complete the order with that key.

### Fix: take over abandoned claims

When the key already exists, has no orderId, has the same request body, and was claimed more than 30 seconds ago, the claim is treated as abandoned. OrderService deletes it with

    idempotency.deleteByKeyAndCreatedAtAndOrderIdIsNull(key, existing.createdAt())

and claims the key again.

- 30 s is far longer than a real request can take with 3 s database timeouts, so a request that is still running is never taken over.
- The delete only removes that exact claim (same createdAt) and only if it still has no order, and it returns 1 or 0. If two retries arrive together, only one gets 1 and takes over; the other gets the normal 409, then MongoDB's unique _id decides the new claim as usual.
- A different body with the same key still gets 422, because the fingerprint must match.

New unit test OrderServiceTests.abandonedClaimIsTakenOver; the existing duplicateKeyWhileFirstRequestRunsIsInProgress still covers a fresh claim returning 409. 39 tests pass.

Same stuck key after rebuilding:

    HTTP/1.1 201
    Location: /orders/6b059ec19d32548c503fb778
    time: 0.534699s

    WARN [40bb65eb-1e4d-4b9d-aa3c-f87facdcd238] ... OrderService : Taking over abandoned Idempotency-Key m15-key-1 claimed at 2026-11-24T14:13:14.358Z
    INFO [40bb65eb-1e4d-4b9d-aa3c-f87facdcd238] ... OrderService : Created order 6b059ec19d32548c503fb778

    > db.orders.countDocuments({customer:'m15'})
    4

    HTTP/1.1 201
    Location: /orders/6b059ec19d32548c503fb778
    Idempotent-Replayed: true
    time: 0.021291s

Exactly one new order for the key, and the next retry replays the same order.

Known gap: if the claim succeeded but the order insert was the write that froze, that order could still land later and a takeover would create a second one. The full fix is to derive the order's _id from the Idempotency-Key, so the order insert itself cannot happen twice.

## Transient failure, uncontrolled retry, safe mitigation

- Transient failure: MongoDB briefly down or slow. The api fails fast with 503 and Retry-After, and recovers by itself when MongoDB is back.
- Uncontrolled retry: a client retrying a timed-out write without an Idempotency-Key (experiment 2), or retrying immediately in a tight loop, which adds load to a database that is already struggling.
- Safe mitigation: short timeouts so threads are not held, 503 with Retry-After, retries only with an Idempotency-Key, exponential backoff with jitter on the client, and recovery of abandoned claims on the server.

## Explained, not built

Retry budgets: limit retries to a small share of total traffic (for example 10%), so that during an outage retries cannot multiply the load.

Backoff with jitter: wait 1 s, 2 s, 4 s ... plus a random amount, so thousands of clients that failed at the same moment do not all retry at the same moment.

Circuit breaker (for example Resilience4j): after many failures in a row, stop calling MongoDB for a short period and return 503 at once, then let a few test calls through. With 2-3 s timeouts the api already fails fast, so I did not add one; it matters more when timeouts are long or the dependency is expensive.

Bulkhead: separate thread pools or connection limits per dependency, so one slow dependency cannot use every request thread.

429 vs 503: 429 Too Many Requests means this client is sending too much (rate limiting, backpressure); 503 means the service cannot handle requests right now. Both can carry Retry-After.

Graceful shutdown: Spring Boot shuts down gracefully by default, finishing in-flight requests before stopping. With the readiness probe from M13, Kubernetes stops sending new traffic first.

Secrets: the MongoDB URI is in .env for Compose and in k8s/11-secret.yaml for Kubernetes. Both are in .gitignore; only .env.example and 11-secret.yaml.example (with placeholders) are committed.

Actuator: only health is exposed by default; beans, mappings and the rest are only in the dev profile. Health shows MongoDB's state, which is how dependency problems show up in monitoring and in Kubernetes readiness.

## Side observation

In the full test run, OrderConcurrencyTests sent 10 parallel creates with one key and got 3x201 and 7x409 this time, where earlier runs got 10x201. Still exactly one order in the database. Which requests see "in progress" (409) and which see the finished claim (201 replay) depends on timing, and both are correct responses.
