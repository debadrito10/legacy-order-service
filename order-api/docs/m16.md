# M16: Unix and process fundamentals

Diagnostic report on the order-api running in the M12 Compose stack.

Sandbox: the api container itself for process state (docker compose exec api bash), and a throwaway Ubuntu container (docker run --rm ... ubuntu:24.04) with the exported log mounted for text analysis. Steps 1 to 4 were read-only. Step 5 stopped the api on purpose, only in this sandbox.

## Summary

- The api runs as non-root user app (uid 1001), as PID 1, idle (load 0.49 on 16 CPUs), 52 threads, 14 open files, 410 MB resident memory.
- Compose sets no memory limit, so the heap can grow to 75% of the Docker VM (~5.7 GB). The M13 Kubernetes limit of 512Mi is tight for a process already at 410 MB after startup: risk of OOMKilled under load.
- The log shows 2 orders created and 1 database outage (503), traceable end to end by correlation id. 39 of 92 lines are stack traces.
- The app can write only to /tmp-style locations, plus an unused Pebble directory. A read-only root filesystem would close that.
- SIGTERM gives a clean 1.2 s graceful shutdown (exit 143). SIGKILL gives no shutdown at all (exit 137).

## 2. Process state (inside the api container)

    $ whoami; id
    app
    uid=1001(app) gid=999(app) groups=999(app)
    $ cat /etc/os-release | head -2
    PRETTY_NAME="Ubuntu 26.04.1 LTS"
    $ ls -l /app
    -rw-r--r-- 1 root root 36181421 Feb  1  1980 app.jar
    $ touch /app/test.txt
    touch: cannot touch '/app/test.txt': Permission denied

The JAR is owned by root and only readable by app, so the app cannot replace its own code. The 1980 date is not a mistake: Spring Boot's Maven plugin gives every entry a fixed timestamp so the same code always builds the same JAR (1980 is the earliest date a ZIP file can hold).

There is no ps in this image, so I read the process from /proc:

    $ cat /proc/1/cmdline | tr '\0' ' '
    java -jar app.jar
    $ grep -E 'Name|State|Threads|VmRSS|VmHWM' /proc/1/status
    Name:   java
    State:  S (sleeping)
    VmHWM:    410364 kB
    VmRSS:    410364 kB
    Threads:        52
    $ ls /proc/1/fd | wc -l
    14

Java is PID 1 because the Dockerfile uses the exec form ENTRYPOINT ["java", ...]. Sleeping means idle and waiting for requests. VmRSS is current memory, VmHWM the peak.

    $ nproc
    16
    $ cat /proc/loadavg
    0.49 0.51 0.45 1/1109 125
    $ grep -E 'MemTotal|MemAvailable' /proc/meminfo
    MemTotal:        8007880 kB
    MemAvailable:    5400796 kB
    $ cat /sys/fs/cgroup/memory.max
    max
    $ df -h /
    overlay        1007G  9.7G  947G   2% /

Load is far below the CPU count, memory and disk have plenty of room.

memory.max = max means Compose puts no memory limit on the container, so MaxRAMPercentage=75 lets the heap grow to 75% of the whole Docker VM, not of a container limit. In Kubernetes (M13) the limit is 512Mi, of which about 384Mi is heap; the remaining ~128Mi must cover threads, class metadata and compiled code. With 410 MB in use right after startup, that is tight. I would raise the limit to about 768Mi, or measure VmRSS under load before going live.

## 3. Log analysis

I exported the log with docker logs order-api-api-1 > api.log in PowerShell. grep found nothing, although the file had 92 lines:

    $ head -c 32 api.log | od -c
    0000000 377 376  \r  \0  \n  \0      \0      \0   .  \0 ...

Windows PowerShell 5.1 writes > redirects as UTF-16 (377 376 is the byte order mark, \0 after every character) with Windows line endings (\r\n). Linux tools expect UTF-8 with \n. Converted with:

    $ iconv -f UTF-16 -t UTF-8 api.log | tr -d '\r' > api-utf8.log

(Out-File -Encoding ascii in PowerShell avoids this in the first place.)

    $ wc -l api-utf8.log
    92 api-utf8.log
    $ awk '{print $2}' api-utf8.log | grep -E '^(INFO|WARN|ERROR|DEBUG)$' | sort | uniq -c
         28 INFO
          2 WARN
    $ grep -o 'Created order [0-9a-f]*' api-utf8.log
    Created order 6b06c479df7cbc5c55d5c044
    Created order 6b06c47adf7cbc5c55d5c045

Two orders, matching the two 201s. No ERROR lines. The 404 and 400 left no log lines at all: they are handled client errors returned as Problem Details, so they cannot be counted from this log; that would need access logs or metrics.

The two warnings are SpringDoc's startup notice and the outage:

    11:20:29.043Z  WARN [e25e7d04-3885-4108-b5d5-a65788534e01] ... ApiExceptionHandler : Database unavailable: Timed out while waiting for a ...

Tracing that one request by its correlation id:

    $ grep 'e25e7d04-3885-4108-b5d5-a65788534e01' api-utf8.log | cut -c1-160
    11:20:27.045Z  INFO [e25e7d04-...] ... org.mongodb.driver.cluster  : Waiting for ...
    11:20:29.043Z  WARN [e25e7d04-...] ... ApiExceptionHandler         : Database un...

The two lines are exactly 2.0 s apart: the serverSelectionTimeoutMS=2000 from M15, visible in the log.

39 of 92 lines are stack-trace lines from two Mongo connection failures. In a real outage these would bury everything else; logging the message once and the trace at DEBUG, or structured JSON logs, would help (M17).

## 4. Where can the app write?

    $ find /app -type f -printf '%M %u %s %p\n'
    -rw-r--r-- root 36181421 /app/app.jar
    $ find / -xdev -type d -writable 2>/dev/null
    /tmp
    /tmp/tomcat.18080.2578361399975267964 (and its work subfolders)
    /tmp/tomcat-docbase.18080.4063427410462193541
    /tmp/hsperfdata_app
    /var/lib/pebble/default
    /var/tmp
    /run/lock
    $ find / -xdev -type f -user app 2>/dev/null
    /tmp/hsperfdata_app/1

-xdev keeps find on the container's own filesystem (skipping /proc and /sys) and 2>/dev/null hides permission errors.

- /tmp and Tomcat's work folders: expected scratch space.
- /var/tmp and /run/lock: standard world-writable folders in Ubuntu.
- /var/lib/pebble/default: belongs to Ubuntu's Pebble service manager, which this app does not use.
- The only file the app has written is /tmp/hsperfdata_app/1, the JVM's performance data for PID 1, which jcmd and jps read (M4).

Recommendation: run with a read-only root filesystem and a writable /tmp only (read_only: true plus tmpfs: /tmp in Compose, readOnlyRootFilesystem: true plus an emptyDir on /tmp in Kubernetes).

## 5. Signals

SIGTERM (what docker compose stop and Kubernetes send first):

    > Measure-Command { docker compose stop api }
    TotalSeconds: 1.2144651
    > docker logs order-api-api-1 --tail 5
    13:27:12.702Z  INFO ... GracefulShutdown : Commencing graceful shutdown. Waiting for active requests to complete
    13:27:12.753Z  INFO ... GracefulShutdown : Graceful shutdown complete
    13:27:12.814Z  INFO ... LifecycleProbe   : LIFECYCLE 4 @PreDestroy: context closing
    > docker inspect order-api-api-1 --format '{{.State.ExitCode}}'
    143

Stopped in 1.2 s of the 10 s Docker allows. Tomcat stopped taking new requests and let active ones finish, then Spring ran its @PreDestroy hooks. Exit code 143 = 128 + 15 (SIGTERM). This only works because Java is PID 1 (exec-form ENTRYPOINT); with the shell form a shell would be PID 1, would not pass the signal on, and Docker would wait the full 10 s and then kill it.

SIGKILL:

    > docker compose kill -s SIGKILL api
    > docker logs order-api-api-1 --tail 3
    13:28:10.084Z  INFO ... OrderApiApplication : Started OrderApiApplication in 6.975 seconds
    13:28:10.199Z  WARN ... SpringDocAppInitializer : SpringDoc /v3/api-docs endpoint is enabled by default ...
    13:28:10.199Z  INFO ... LifecycleProbe : LIFECYCLE 3 ApplicationReadyEvent: every bean built, Tomcat accepting requests
    > docker inspect order-api-api-1 --format '{{.State.ExitCode}}'
    137

No shutdown lines at all: SIGKILL cannot be caught, so in-flight requests are cut off and nothing is cleaned up. Exit code 137 = 128 + 9 (SIGKILL). In Kubernetes, 137 on a pod usually means OOMKilled, which ties back to the memory finding in section 2.

## How I investigated without disrupting anything

- Read state from /proc, /sys and ls instead of tools that change anything.
- Analysed a copy of the log in a separate --rm container, not on the running service.
- The only write attempt (touch /app/test.txt) was expected to be refused, and was.
- Stopping the api was deliberate, in the sandbox only, and it was restarted afterwards with docker compose start api.
