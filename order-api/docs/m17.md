# M17 - Logging, metrics and tracing

Exit check: "Can isolate application, JVM and dependency symptoms using correlated evidence."

## What I built

- `stub/GstStub.java` - a fake GST-rate service (JDK HttpServer). Arguments: port, delay in ms, fail every Nth call. It prints the X-Correlation-Id it receives.
- `GET /orders/{id}/gst` (GstController) - reads the order, then asks the stub for the rate.
- `GstClient` - RestClient with a 1 s connect and 2 s read timeout. An interceptor copies the correlation ID from the MDC into the outgoing X-Correlation-Id header.
- `ApiExceptionHandler` - RestClientException becomes 502 `gst-unavailable`.
- `application.yaml` - `noduco.gst.base-url`, and `/actuator/metrics` exposed.
- `application-json.yaml` - structured (ECS JSON) console logs with `--spring.profiles.active=json`.
- `docs/m17-load.ps1` - sends N requests one after another and prints error rate and p50/p95/p99/max.
- All 39 tests still pass.

## One request across two processes

Request with `X-Correlation-Id: m17-trace-1` returned 200 `{"orderId":"6b08763f7c39caf404ea8f2d","amountPaise":10000,"ratePercent":18,"gstPaise":1800}`.

Same ID in both processes (from the baseline run):

    API : INFO [base-72] ... GstClient : GST rate 18% in 3 ms
    stub: call=75 correlationId=base-72 delayMs=0 status=200

A request sent without the header gets a UUID from CorrelationIdFilter, and that UUID is forwarded too (stub: `call=11 correlationId=c51a7bab-e5cf-41d6-91ad-642121cbde9b`).

## Isolating the symptom

| Symptom | Correlated evidence | Where the problem is |
|---|---|---|
| Slow, no errors | Each `slow-N` log line shows the GST call took 1,508-1,517 ms; request p50 1,524 ms; same IDs in the stub | Dependency is slow |
| 25% errors, still fast | 25 server 502s = 25 client 500s; `WARN [fail-4] GST service failed: 500 Internal Server Error`; stub shows `fail-4 ... status=500` | Dependency is failing |
| All 502 at about 2.0 s | `WARN [timeout-1] ... Request cancelled`; p50 2,012 ms while the stub takes 2,500 ms | Dependency too slow; our 2 s read timeout cut it off |
| 404 straight away | `"title":"Order not found","correlationId":"m17-app-1"`; no `m17-app-1` line in the stub | Application data; the dependency was never called |
| Is it the JVM? | `GC.heap_info`: 52,045K used of 88,064K committed. JFR over the slow run (240 s): no GC pause events, 687 thread-park events | No - the JVM was idle and waiting |

## JVM diagnostic artifacts

- `target/m17.jfr` - 240 s from 18:19:06 IST, covers the slow run.
- `target/m17-failures.jfr` - covers the failing and timeout runs.
- Both stay local (`target/` is gitignored).
- Heap reserved was about 4 GB because I ran the plain jar on my laptop. In Docker/Kubernetes, `MaxRAMPercentage=75` of the 512Mi limit applies instead.

## What did not go as planned

- Thread dump: I tried four times to catch a request while it waited on the stub. Each dump landed between requests (the last one, at 18:36:37, shows every Tomcat thread idle). I don't use it as evidence; the log timings and JFR cover it.
- The timeout log says "Request cancelled", not "timed out". The JDK HTTP client cancels the request when the read timeout fires. The 2,012 ms timing is what shows it was the timeout.
- p99 of 150 ms in the failing run is higher than the baseline. Probably the error path (WARN log + 502 body). Not investigated.
