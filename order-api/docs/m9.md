# M9: MongoDB modelling, queries and indexes

## The query

`GET /orders/history?customer=c42&status=PAID`, which runs
`find({customer: 'c42', status: 'PAID'}).sort({createdAt: -1}).limit(20)` against 50,010 orders.

## Before and after the index

| | Before | After |
|---|---|---|
| Plan | COLLSCAN, then SORT | IXSCAN, FETCH, LIMIT (no SORT) |
| Docs examined | 50,010 | 17 |
| Keys examined | 0 | 17 |
| Returned | 17 | 17 |
| Time (ms) | 33 | 0 (first run 12, 9 of it planning) |

Without an index Mongo read every order and sorted the matches in memory. With it, it reads exactly the 17 it returns.

## The index

`{customer: 1, status: 1, createdAt: -1}`, declared with `@CompoundIndex` on `OrderDocument` and built at startup (`auto-index-creation: true`).

The order of fields matters. customer and status come first because the query wants exact values for both, so Mongo jumps straight to the c42/PAID block. createdAt comes last because inside that block the entries are already newest first, so Mongo reads them in order and stops at the limit. That's why there's no SORT stage. With createdAt first, c42's PAID orders would be scattered through the whole index and Mongo would scan far more keys.

## Data model

An order is one document (customer, amountPaise, currency, status, createdAt, version), so one read gives the API everything.

Idempotency records sit in their own collection and point to the order by `orderId`. They're looked up by key, exist before the order does, and expire on their own, so embedding them would be wrong.

My rule: embed what is always read with its parent and doesn't grow without limit (like line items). Reference what is queried on its own, shared, or can grow large.

## Trade-off

Reads dropped from 50,010 docs to 17. The cost is on writes: every insert, and every update that changes status, also updates the index, and the index takes disk and memory. So I only index queries the app actually runs, and I prefer one index shaped like the query (equality fields, then sort) over several single-field ones.

Signs of a missing or wrong index: docs examined far above docs returned, or a SORT stage in the plan.
